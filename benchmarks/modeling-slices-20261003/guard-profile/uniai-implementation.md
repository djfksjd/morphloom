I did not run tests or inspect photos or frame renders. The reported targeted tests and typecheck do not cover these defects:

- **A 0.1 batch can execute a 0.2-only curve edit.** `applyAssemblyComponentBatchPatch` constructs a patch with its derived `schema`, then spreads the runtime `edit` over it. An edit supplied as JSON can include `schema: 'morphloom.component-patch/0.2'`, overriding the derived 0.1 schema and passing the curve-operation gate. The same spread can override `operationId` and `expectedInputFingerprint`. Reject these fields on batch edits at runtime, or spread the edit before assigning trusted fields.

- **A malformed point delta passes validation.** `finiteVector` and `finiteVector2` return true for `undefined`, so a delta entry with a valid `pointIndex` but no `deltaMm` passes `validGeometryPatch`. Applying it then dereferences the missing delta in `addVector` or the profile-point arithmetic, producing a runtime `TypeError` instead of the declared unsafe-patch rejection. Require `deltaMm` to be present before checking its bounds.

- **The editor can apply a stale draft to a new IR.** Draft reset is in an effect, but `apply()` takes the current `ir` and component while reading the existing draft. After an IR/selection change, there is a render before that effect resets the draft; applying in that interval fingerprints the *new* source, so the later `latest.current !== source` check does not detect that the inputs belonged to the previous component or IR. This can write old control-point or material values to the newly selected component. Bind each draft to its source fingerprint and component ID and reject mismatches before constructing a patch.
